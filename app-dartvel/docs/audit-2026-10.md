## Earlier claims checked

The first audit and the PR #3 fix commit (6e7bc90b9) were written without running anything:

- The fix commit **did not compile** (`BytesBuilder` without `dart:typed_data`, `unawaited`
  without `dart:async`, `restoreNetwork` missing from two `VpnService` implementations). The
  audit's "tests pass (code inspection)" was therefore false. Fixed in 817a5ffb3.
- The project depended on a private host checkout of Dartvel (`path:` dependencies), so nobody
  else could resolve it. It now uses the published `^0.12.2` packages.
- The netns test had not been run; it now runs and passes (below).
- The OpenVPN fixture tests read a private host path and **returned early, passing**, when the
  file was missing. They now read the submodule's fixtures and fail if those are absent.
- `tool/tunnel_helper/probe.dart` still wrote the profile (with the private key) to a temp file.

## Linux helper (PR #3), completed

Fixed in the review of PR #3 and verified here:

1. **Profile via stdin with a size limit.** `partout-tunnel --stdin` reads the profile as the
   first stdin line (≤ 4 MiB, `kMaxHelperProfileBytes`); there is no path argument
   (`partout-tunnel /etc/shadow` → usage, exit 64). Checked on the built binary: invalid input →
   `{"type":"error","code":"profile_invalid"}`, a 5 MiB line → `profile_too_large`, empty stdin →
   `profile_missing`, none of them echoing input.
2. **No temp file with the private key**: not in `TunnelProcess` (tested: no file appears), not in
   `probe.dart`, not in the netns test (the profile is built in-process and piped; the server key
   goes to `wg` on stdin).
3. **No file content in errors.** Error events carry a fixed code and at most the failure's type
   (`HelperError.fromFailure`); the `network_setup` error used to carry the exception text.
4. **The app calls `--cleanup`**, and only when needed: a helper that started (`ready`) and ended
   without reporting `{"type":"network","state":"restored"}`. A refused pkexec prompt no longer
   triggers a second prompt. Diagnostics has "Restore network" for the case where the app died too.
5. **Honest netns claim**: the test now exists in Dart and was run (below).

Found and fixed while running it for real:

- **"Connected" before anything was routed.** The engine reported `connected` seconds before the
  helper had addressed the tun device and installed routes. The helper now holds `connected`
  until the device is configured (`HelperStatusGate`).
- **The helper never exited after `stop`.** It restored the network and then kept running,
  because its stdin subscription was never released. Every disconnect in the app would have hit
  the 5 s timeout, SIGTERM, and a spurious `--cleanup` password prompt.

The helper's events are now a sealed `HelperEvent` type; JSON exists only on the stdio wire
(`tunnel_protocol.dart`).

### Real tunnel in network namespaces

`dart run tool/netns_test/run.dart` (replaces `run.sh` and `make_profile.dart`) runs the real
helper and engine in a client namespace against a WireGuard server in another, joined by a veth
pair. This kernel has no WireGuard module, so the server end was `wireguard-go`; the client side
is Partout's own wg-go. 25 checks passed, among them: handshake and `connected`; the tun device
addressed by the helper; ping through the tunnel and encrypted bytes counted by the server; stop
removes rules and the device; an excluded route leaves outside the tunnel; the kill switch drops
outside traffic, still drops it after the helper is killed with SIGKILL, and `--cleanup` lets it
through again; the host's rules, routes and nftables tables unchanged. Output:
docs/evidence/netns-2026-10-15.txt.

Not covered: the pkexec/polkit prompt on a desktop, systemd-resolved DNS, IPv6 through the
tunnel, roaming. Known limits of the network plan are in docs/TUNNEL.md (endpoint bypass, the
kill switch does not cover forwarded container/VM traffic, IPv6 leak without the kill switch,
resolv.conf written through a symlink).

## Conventions

Checked by `test/conventions_test.dart` (the published CLI has no conventions check):

- `main.dart` is the smallest form around `DV.run(...)` with a TODO: 0.12.2's `DV.run` cannot take
  the launch arguments or startup work. App widget and startup: `lib/app.dart`.
- `lib/pages/index.dart` and `lib/pages/_guard.dart` (a URL for a missing profile returns to the
  list; tested).
- Widgets are `@DVFunctionalWidget` functions built from `DVBox`/`DVText`; no
  `StatelessWidget`/`StatefulWidget`, `Text`, `SelectableText` or `Container` in app code; local
  state is signals; icon buttons are `DVIconButton`; tappable rows, toggles and pickers carry
  tooltips. `dartvel doctor` and `dartvel build` run Dartvel's tooltip lint.
- Backend functions: typed (`String` in and out); the import endpoint has `bodyLimit` and
  `rateLimit` middleware through `@DVUseMiddleware`, because 0.12.2 has no `middleware:` field on
  `@DVBackendFunction` (TODO in the code). An unused template function that wrote personal data
  to a file on the server is removed.
- JSON remains only at listed boundaries (the engine ABI and profile document, the helper
  protocol and state file, the credits asset, and the file-backed stores). The stores are the
  part that should become Dartvel models; see the device-only model gap.
- Dart-only tooling: the helper build, the netns test and the icon generator are Dart; the bash
  scripts are gone. No private host paths in the repository text (checked by the test).
- App icon and favicon: `assets/app_icon.png` (1024 px, opaque) and `assets/favicon.png`, derived
  from the logo by `tool/icons.dart`, declared as `dartvel.pwa.icon` and `dartvel.seo.favicon`.
