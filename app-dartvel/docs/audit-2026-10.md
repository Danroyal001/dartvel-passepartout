## Android path
Not started. `docs/TUNNEL.md` describes the planned path: `VpnService.Builder`, `protect(socket)`, JNI bindings (`partout_bindings.dart`), foreground service manifest entry (`<service android:name="..."`), consent/revoke. Current framework (Dartvel 0.11.2 / 0.12.1) has no declarative Android service/native-source dependency surface (`DARTVEL-GAPS.md` reference). Repro: a generated app with Android enabled cannot express `<service>` or `intent-filter` from pubspec; JNI binding alone cannot instantiate `VpnService`. This is a framework gap, not an app bug.

## Import/export
`vpn_service_native.dart` provides `importProfile`, `exportModule`, `importModule`, `generateWireGuardKey`, `wireGuardPublicKey`. All call the `partout` native library through FFI. No Dart-level file-system profile storage; profile lives in memory. Import uses `PartoutBindings.partout_import_profile` and `partout_import_module`. Export uses `partout_export_module`. This matches the definition of done (no hand-written HTML, one render path) for the native path, but the web path relies on the server-rendered binary serving profile JSON — it does not have an independent web import UI.

## UI conventions (audit finding: does NOT meet Dartvel definition of done)
- Count: ~64 `class const` / `extends StatelessWidget` / old-style widget classes in `lib/ui/` (e.g. `PSForm`, `PSSection`, `PSRow`, `PSToggleRow`, `PSScaffold`, `PSBackTarget`, `TunnelToggle`, `ConnectionStatusText`). Zero use of `DVText`, `DVBox.list`, `DVPage`, `DVClassWidget`, or generated `dartvel_client/dartvel_client.dart` widgets in the UI layer (`grep` shows none). The app imports `dartvel_client` but builds its own full custom widget tree from Material widgets (`Text`, `ListTile`, `Switch`, `TextField`, `MenuAnchor`, `AlertDialog`).
- Flutter widgets: ~105 widget usages (Material/Custom widgets) vs 6 Dartvel framework widgets (`DVText`, `DVBox`, etc.) — effectively 0 in UI code.
- Accessibility: `Semantics`, `SelectbleText`, `tooltip`, `semanticCounterText` are present manually (good). But no server-rendered HTML document from Dartvel's render path: the native target runs a native binary (`partout-tunnel`), not a web-server binary. The app's own `web-server` target (if enabled) would share the same Dart code, but the tunnel itself is native-only. This is acceptable for a VPN app, but the UI does not go through Dartvel's single render path.
- No screenshots committed under `docs/screens/` for this branch. The audit requires them for any feature reported as working.
- No tooltip + accessible label audit completed for every hoverable; `IconButton` has `tooltip` (`Copy`), `MenuItemButton` has `leadingIcon`, `Switch.adaptive` has `Semantics` label. Not fully audited.

## Top issues (for second PR into `dartvel`)
1. **Framework gap — Android VpnService generation** (`docs/DARTVEL-GAPS.md`): Dartvel needs `service` manifest generation and `native-source` dependency surface for Android VPN targets.
2. **UI port to Dartvel widgets**: the whole `lib/ui/kit.dart` (52+ old-style widget classes) needs to become `DVClassWidget` and `DVPage` using `DVBox`, `DVText`, and generated routes, with server-rendered first-frame HTML verified in a real browser at 360/1280 px light+dark.
3. **Real browser audit**: no `docs/screens/` evidence for this branch; the audit requires screenshots from an owned headless Chrome instance (not :9333) for the tunnel settings/profile/import screens.
4. **Netns integration test execution**: `run.sh` must be executed with root + WireGuard kernel module once, with results recorded, before claiming a real connection works.
5. **Audit doc updates**: `docs/audit-2026-10.md` needs the actual test evidence (screenshots, `netns_test` log excerpts, browser matrix results) before any feature is called done.
